# MT-01 — чеклист внедрения компаний WareTrack

Дата: 29 октября 2026 года. Статус: план будущего внедрения, не свидетельство выполненных миграций или тестов.

Архитектура и точные пути: [multi-tenancy.md](multi-tenancy.md). Пустые флажки означают, что этап ещё не подтверждён. Для каждого gate исполнитель фиксирует дату, версию кода/схемы, среду, результат тестов и ссылку на доказательства. Успешный UI-сценарий без прямых API-проверок недостаточен.

## G0. Подготовка — MT-01

- [ ] Спецификация рассмотрена: глобальный ADMIN; локальные VADITAJS/LIETOTAJS; глобальный USER пока сохраняется.
- [ ] Подтверждены отдельные CompanyMembership и CompanyJoinRequest, JWT идентичности, явный companyId в маршруте.
- [ ] Назначен ответственный за ручное сопоставление прежних записей и пользователей; владелец не выводится из названия товара или автора события.
- [ ] Зафиксировано решение по частичным перемещениям либо отмечен запрет перехода к MT-09 до решения.

Приёмка: границы архитектуры и открытые вопросы видны; существующие данные не изменены. Проверка MT-01 — чтение исходников и контроль границ двух документационных файлов, без запуска backend.

## G1. Безопасная база разработки — MT-02 → MT-03

- [ ] MT-02: импорт приложения тестами не создаёт/не открывает рабочую БД; временная тестовая БД задаётся до любых побочных действий.
- [ ] Foreign keys включены на каждом тестовом соединении; попытка нарушить FK действительно отклоняется.
- [ ] Существующие 13 тестов выполняются на изолированной БД; никаких операций seed с рабочими данными.
- [ ] Обычный запуск приложения проверен отдельно: устранение import-time побочного эффекта не оставляет новую среду без способа подготовки схемы.
- [ ] MT-03: baseline сверяется с реальной схемой, неизвестная схема не получает слепой stamp.
- [ ] Пустая БД создаётся миграциями, существующая копия проходит переход; проверено восстановление.

Приёмка: тестовый контур безопасен, версии схемы контролируются. До G1 нельзя использовать текущий pytest-import как безопасный способ проверки миграции.

## G2. Схема и владение — MT-04 → MT-05; MT-06 после MT-04

- [ ] Новые сущности имеют UNIQUE/FK/CHECK, а одна пара user/company — не более одного membership и одного PENDING.
- [ ] Есть утверждённый реестр таблица/ID → компания, включая события, перемещения и связанные справочники.
- [ ] Есть отдельный реестр user_id → компания/роль; назначены первые руководители через ADMIN.
- [ ] Несогласованная строка блокирует backfill; компания прежней системы не создаётся без решения владельца.
- [ ] На копии после backfill сохранены ID, хеши паролей, активность аккаунтов, количества записей и предметные значения.
- [ ] Граф связей не содержит cross-company ссылок; для неоднозначного журнала зафиксировано решение.
- [ ] MT-06: контекст компании проверяет пользователя, компанию, membership/системное полномочие и разрешение на каждый запрос.

Тесты: дубли и неверные статусы; повторный backfill/частичная ошибка; несопоставленные записи; неактивные user/company; PENDING/REJECTED/revoked; ADMIN без членства через явный системный путь.

Приёмка: модель и доступ готовы на тестовой среде. **Новые компании ещё не доступны реальным пользователям.**

## G3. Полная серверная изоляция — MT-07 → MT-08 → MT-09 → MT-10 → MT-11 → MT-12

- [ ] MT-07: все методы категорий, поставщиков и мест ограничены company_id.
- [ ] MT-08: list/detail/create/update/delete товаров и все входящие FK проверяют компанию; пагинация и totals согласованы.
- [ ] MT-09: решение об остатках утверждено; частичное завершение учитывается корректно либо явно запрещено согласованной политикой.
- [ ] Исторические частичные done не используются для автоматического восстановления фактических остатков без сверки.
- [ ] Резервирование, завершение и отмена атомарны; конкуренция не создаёт отрицательные остатки и двойное движение.
- [ ] MT-10: отчёты/dashboard фильтруют до aggregate/limit; журнал не раскрывает соседние компании.
- [ ] MT-11: User + PENDING создаются транзакционно, approval + membership + audit также; отказ доступа не предоставляет.
- [ ] Повторная заявка сохраняет историю; параллельные решения не создают дубликаты.
- [ ] MT-12: VADITAJS управляет только участниками своей компании и не вызывает глобальные административные изменения User.
- [ ] Последний руководитель/ADMIN защищён в том числе при параллельных запросах.

Тесты: все сценарии матрицы безопасности ниже; нормальный CRUD внутри одной компании; одинаковые SKU/имена между компаниями; неверные составные FK; одобрение/отказ/повтор; self-approval; смена глобальной и локальной активности.

Приёмка: каждый серверный путь учтён, включая старые маршруты. Не включать пользовательский доступ к компаниям только потому, что форма регистрации уже готова.

## G4. Клиент и закрытие обходов — MT-13 → MT-14 → MT-15

- [ ] Query keys включают userId/companyId; формы и query functions используют компанию конкретного маршрута.
- [ ] Logout/401/смена аккаунта очищают кеш; задержанный ответ не возвращает старые данные.
- [ ] Смена компании не переносит форму, результаты или права; завершение старой мутации инвалидирует исходную компанию.
- [ ] Две вкладки с разными компаниями работают независимо; logout синхронизирован.
- [ ] Отзыв членства приводит к очистке его данных и возврату на `/companies`, не блокируя другие членства.
- [ ] Регистрация ведёт на «Jūsu uzņēmumi»: PENDING виден отдельно, доступных компаний сначала нет.
- [ ] Approval добавляет компанию после обновления данных; REJECTED не открывает склад.
- [ ] Старые ссылки перенаправляются безопасно; отсутствует выбор компании по неявному default.
- [ ] Старые unscoped endpoints закрыты либо имеют тот же проверяемый контекст, без глобального чтения.
- [ ] Публичные `/api/items`, `/api/categories` и `/catalog` не раскрывают внутренний склад. Если публичный каталог сохранён, отдельно утверждены публикация и сокращённый DTO, и это проверено напрямую по API.

Тесты: E2E полный цикл регистрации/решения/входа, прямые URL, разные роли одного пользователя, переключение аккаунта/компании, ошибки и поздние ответы, список всех старых маршрутов.

Приёмка: frontend и backend используют один контракт; никакой старый путь не обходит изоляцию. **Открытие компаний всё ещё требует G5 и G6.**

## G5. Финальная схема и демоданные — MT-16 → MT-17

- [ ] Нет tenant-строк без company_id, кроме явно выделенных глобальных системных событий.
- [ ] Введены NOT NULL, составные FK и tenant-UNIQUE; все старые пути записи устранены.
- [ ] Проверена nullable-ссылка Supplier: удаление не обнуляет company_id товара; согласованы RESTRICT/архивация.
- [ ] SQLite foreign_key_check и integrity_check на миграционной копии не показывают проблем.
- [ ] Сверены прежние ID, парольные хеши, значения, история и связи с утверждённым реестром.
- [ ] Демо SIA TechStore / SIA AutoParts / SIA BuildMaster создаются независимыми наборами после полной изоляции.
- [ ] Двойной запуск demo-seed не меняет имеющиеся записи и пароли; конфликт сообщает ошибку, сбой откатывается.

Тесты: прямые нарушения FK/UNIQUE/CHECK на отдельной БД, миграция заполненной копии, сохранность legacy, идемпотентность seed, отсутствие cross-company ссылок.

Приёмка: целостность защищена БД и API, demo не является источником потери legacy. Seed не выполняется автоматически при старте или миграции.

## G6. Выпуск и восстановление — MT-18

- [ ] Пройдены G1–G5, нет нерешённых вопросов владения/учёта, влияющих на выпускаемые данные.
- [ ] Все 35 существующих прикладных операций и все новые операции отражены в регрессионной матрице; намеренные изменения публичного доступа документированы.
- [ ] В production отсутствуют fallback JWT secret и демонстрационные пароли; глобальные административные действия журналируются.
- [ ] Подготовлена согласованная версия frontend/backend/схемы и способ остановки доступа/записей.
- [ ] Создана согласованная резервная копия, проверено восстановление в отдельную БД и вход старых пользователей.
- [ ] На время backfill исключены новые несопоставленные записи; проверены контрольные количества/значения до и после.
- [ ] Проведён smoke-test выбранных компаний: вход, CRUD, transfer, отчёты, заявки, отзыв доступа.
- [ ] Только после фиксации результатов открыт доступ пользователей к нескольким компаниям.

Условие остановки выпуска: любая утечка чужой строки/агрегата/имени, несопоставленные legacy-данные, ошибка миграции, неверные остатки или невозможность восстановления. Флаг UI сам по себе не является release gate: запрет доступа должен действовать на сервере.

## Матрица обязательных проверок IDOR и утечек

Использовать минимум компании A/B/C, одинаковые SKU/названия в A/B, разные контрольные остатки, сотрудника A, руководителя A, пользователя с VADITAJS в A и LIETOTAJS в B, пользователя без членств, PENDING/REJECTED/revoked, глобального ADMIN.

| Проверка | Ожидаемый результат |
|---|---|
| JWT отсутствует/испорчен/истёк; user неактивен | Нет складского доступа |
| Валидный JWT без активного membership | Нет складского доступа, доступны только разрешённые identity-сценарии |
| Подмена companyId в URL, query, body, headers | Контекст не обходится; body не назначает владельца |
| GET/PUT/PATCH/DELETE по ID объекта B в маршруте A | Нейтральный отказ/404, объект B не читается и не меняется |
| POST/PUT с category/supplier/location/item/source/destination ID из B | Отказ без раскрытия чужой сущности, нет побочных записей |
| Списки, поиск, status/category filters, totals, pagination | Только A; фильтрация до подсчёта и ограничения |
| Dashboard/reports/top-N/activity | Только данные A, включая текст событий и имена |
| Прямое обращение к прежним публичным/unscoped endpoint | Нет обхода новой защиты |
| VADITAJS A решает заявку B, меняет роль User или назначает ADMIN | Отказ; проверяется backend |
| Самоодобрение; повторное/конкурентное решение | Отказ/конфликт, не возникает лишнего membership |
| Отзыв membership с прежним JWT | Следующий запрос запрещён; B остаётся доступной при её членстве |
| Глобальный ADMIN без membership | Явный системный доступ к выбранной компании, аудит, без смешения данных |
| Прямая cross-company запись на тестовой БД | Составной FK отклоняет запись |
| Переключение с задержанным запросом/мутацией | Данные и инвалидация остаются в исходном контексте |
| Logout → вход другого пользователя, две вкладки | Нет старых данных/прав в UI или кеше |
| Сбой посередине транзакции регистрации/approval/transfer | Нет частично выданного доступа или частичного изменения остатков |

## Резервная копия и откат

До каждой рабочей миграции определить фактический DATABASE_URL и resolved путь; не предполагать, что используется default `backend/waretrack.db`. Зафиксировать версию приложения, ревизию схемы, время, контрольную сумму резервной копии и сверки таблиц, ответственного за восстановление. Секреты не помещать в отчёты.

Для SQLite использовать согласованный backup при остановленных писателях либо штатный механизм согласованной копии; не копировать произвольно активный файл, игнорируя WAL. Восстановление проверить в отдельном месте до рабочего перехода.

При неуспехе: закрыть доступ и записи, сохранить диагностику, восстановить согласованную пару БД/приложение, повторить сверки и smoke-tests. Новые записи после backup требуют отдельного плана сохранения/согласования; нельзя молча потерять их. Не обещать безусловный downgrade. Старое приложение с глобальными запросами нельзя возвращать поверх многокомпанейской БД.
