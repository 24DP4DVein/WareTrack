# MT-01 — архитектура нескольких компаний WareTrack

Дата проверки: 29 октября 2026 года. Статус: архитектурная подготовка; функциональность компаний НЕ реализована.

Документ описывает проверенное состояние рабочей папки и целевую архитектуру. Раздел 1 — существующее поведение; разделы 2–10 — требования к будущей реализации. Все пути указаны относительно корня проекта. План развёртывания: [multi-tenancy-checklist.md](multi-tenancy-checklist.md).

В MT-01 разрешены только этот файл и `docs/multi-tenancy-checklist.md`. Код, схема, данные, глобальное значение `USER` и существующие документы не изменяются. Коммит и push не выполняются.

### 1.2. Идентичность и текущие права

`backend/app/auth/security.py`: `hash_password`/`verify_password` используют Argon2; `create_access_token` создаёт HS256 JWT с `sub` и `exp`; `decode_access_token` проверяет токен. Срок по умолчанию — 480 минут. При отсутствии `JWT_SECRET_KEY` применяется встроенный демонстрационный секрет.

`backend/app/auth/dependencies.py`: `get_current_user` проверяет Bearer JWT и заново читает активного пользователя из БД; `require_admin` требует `user.role == "ADMIN"`.

`backend/app/routers/auth.py`:

- POST `/api/auth/register`, `register`: нормализует email, создаёт активного `USER`, сразу выдаёт JWT. Компании и ожидания одобрения нет.
- POST `/api/auth/login`, `login`: проверяет пароль и активность, выдаёт JWT.
- GET `/api/auth/me`, `me`: возвращает текущего пользователя.

Исполняемые значения роли — только `USER` и `ADMIN`: `backend/app/schemas/__init__.py` (`UserOut`, `UserUpdate`), `src/types/index.ts` (`Role`). `LIETOTAJS` и `VADITAJS` как роли не реализованы. Подпись «Lietotājs» в UI соответствует `USER`.

### 1.3. Модели и владение

Все модели находятся в `backend/app/models/__init__.py`. У всех PK `id`; `company_id` отсутствует.

| Класс / таблица | Основные связи и ограничения |
|---|---|
| `User` / `users` | Глобально уникальный email; пароль, строковая роль, активность; связи с Transfer и ActivityLog |
| `Category` / `categories` | Глобально уникальное name; связь с Item |
| `Supplier` / `suppliers` | Глобально уникальные name/email; связь с Item; поле category — текст, не FK |
| `Location` / `locations` | Глобально уникальный code; capacity; связь с Item |
| `Item` / `items` | Глобально уникальный sku; FK category/location RESTRICT, nullable supplier SET NULL; stock, min_stock, price Float |
| `Transfer` / `transfers` | Уникальный code; FK item, source/destination location, creator; quantity, status, priority |
| `ActivityLog` / `activity_logs` | Nullable FK user; entity_type/entity_id без FK на предметный объект; message |

Отдельных Company, Membership, JoinRequest и остатков по местам нет. Каждый Item имеет один `location_id` и один `stock`. Владельца старого набора данных по этим моделям установить нельзя.

`database.py` включает `PRAGMA foreign_keys=ON` для SQLite engine приложения. SQL CHECK для допустимых ролей, статусов и неотрицательных остатков в моделях не объявлены; часть правил существует в Pydantic.

### 1.4. Frontend, кеш и существующие маршруты

`src/app/` содержит `/login`, `/register`, `/catalog`, `/`, `/items`, `/categories`, `/locations`, `/suppliers`, `/transfers`, `/reports`, `/users`, `/settings`, `/help` (соответствующие `page.tsx`). `/companies` отсутствует.

`AppShell` оставляет публичными `/login`, `/register`, `/catalog`; остальные маршруты требуют наличия токена в клиентском состоянии. `/users` и `/settings` дополнительно проверяют ADMIN. Это не серверная защита. `src/app/login/page.tsx` (`Login`) и `src/app/register/page.tsx` (`Register`) после успеха переводят на `/`.

`src/store/useAppStore.ts`: JWT и user сохраняются Zustand persist под ключом `waretrack-auth` в стандартном localStorage. `logout` очищает только token/user. `src/components/layout/Topbar.tsx` переводит на `/login`. `src/lib/api.ts` вызывает logout при 401. Серверного отзыва JWT при выходе нет; вызов `/auth/me` при восстановлении сессии не найден.

`src/hooks/useWarehouse.ts`: ключи кеша общие (`items`, `categories`, `locations`, `suppliers`, `transfers`, `dashboard`, `reports`, `users`), без пользователя/компании. QueryClient создаётся в `Providers` и не очищается при logout. `useItems` отправляет `pageSize`, тогда как `list_items` принимает `page_size`: контракт требует исправления. Изменения товара не инвалидируют все связанные показатели категорий и мест.

### 1.5. Перемещения, тесты и seed

`backend/app/routers/transfers.py`, `transfer_create`: проверяет существование товара/мест, соответствие исходного места, доступный остаток с вычетом pending/in-transit резервов. Специальная защита конкурентного резервирования не реализована.

`transfer_status`: разрешает pending → in-transit/cancelled и in-transit → done/cancelled. При done меняет `Item.location_id` только если `quantity == item.stock`. Частичное завершение не создаёт остаток в месте назначения и не уменьшает остаток источника. Отчёт при этом учитывает завершённое количество. Существующая история не доказывает фактическое размещение остатков.

`backend/tests/conftest.py`: импортирует `app.main` до подмены `get_db`; следовательно, import-time create_all может затронуть обычную БД. Тестовый SQLite engine отдельный, явное включение FK на нём отсутствует. `fresh_database` пересоздаёт in-memory таблицы. `backend/tests/test_auth.py`, `test_items.py`, `test_transfers.py` содержат 13 тестовых функций; проверок компаний нет.

`backend/app/seed.py`, `seed`: вызывает create_all и пропускает всё заполнение при наличии любого User; иначе создаёт демонстрационный общий набор. Он не пригоден для дозаполнения трёх компаний в существующей БД.

## 2. Утверждённая целевая модель ролей

Одна общая БД и схема с явным владением складскими строками. Глобальная идентичность хранится в User; доступ и локальная роль — в CompanyMembership. Пользователь может состоять в нескольких компаниях с разными ролями.

- `ADMIN` остаётся глобальным системным администратором: все компании, назначение первых руководителей, рассмотрение заявок любой компании.
- `VADITAJS` — руководитель только указанной компании.
- `LIETOTAJS` — сотрудник только указанной компании.
- Глобальный `USER` сохраняется; он не переименовывается в MT-01 и сам по себе не даёт складского доступа после перехода. Локальная роль добавляется при миграции членства.
- JWT представляет глобальную идентичность, не хранит авторитетные права членства. Отзыв членства должен действовать на следующем запросе с прежним JWT.
- Для ADMIN предусмотрено явное системное полномочие вместо обязательного членства во всех компаниях. Зависимость всё равно проверяет активность ADMIN, выбранную компанию и допустимость операции; складские запросы остаются ограниченными одной компанией. Этот путь журналируется, не создаёт фиктивного одобрения членства.

### Матрица целевых разрешений

| Операция | Пользователь без членства / PENDING / REJECTED | LIETOTAJS | VADITAJS | Глобальный ADMIN |
|---|---|---|---|---|
| Свой профиль, свои заявки, «Jūsu uzņēmumi» | Да | Да | Да | Да |
| Склад, отчёты, история компании | Нет | Только своя | Только своя | Выбранная компания |
| CRUD товаров и допустимые перемещения | Нет | Своя компания | Своя компания | Выбранная компания |
| Изменения категорий, мест, поставщиков | Нет | Нет | Своя компания | Любая компания |
| Просмотр участников и заявок компании | Нет | Нет | Своя компания | Любая компания |
| Одобрение/отказ заявки | Нет | Нет | Своя компания | Любая компания |
| Отзыв членства сотрудника | Нет | Нет | Своя компания | Любая компания |
| Назначение/смена VADITAJS | Нет | Нет | Нет, первоначально зарезервировано ADMIN | Да |
| Глобальная активность User, глобальная роль ADMIN | Нет | Нет | Нет | Да, системная операция |
| Создание/деактивация Company | Нет | Нет | Нет | Да |

Последняя таблица задаёт консервативную политику первой версии: руководитель принимает сотрудников как LIETOTAJS и не назначает других руководителей. Делегирование этого полномочия требует отдельного решения. Нельзя одобрять собственную заявку, повышать себя из тела запроса, снимать последнего активного руководителя действующей компании или последнего активного ADMIN. Проверки должны выдерживать конкурентные запросы.

Деактивация глобального User блокирует все компании; отзыв одного membership не влияет на другие. Руководитель не получает существующий глобальный `user_update`.

## 3. Сущности и жизненный цикл

| Новая сущность | Поля и инварианты |
|---|---|
| `Company` / `companies` | id, уникальный стабильный slug, name, is_active, created_at/updated_at. Создание ADMIN; до назначения первого руководителя недоступна для заявок. Деактивация запрещает складские операции и новые заявки, сохраняя историю |
| `CompanyMembership` / `company_memberships` | id, company_id, user_id, role (`LIETOTAJS`/`VADITAJS`), is_active, approved_at/by, revoked_at/by; UNIQUE(company_id,user_id); FK на Company/User |
| `CompanyJoinRequest` / `company_join_requests` | id, company_id, user_id, status (`PENDING`/`APPROVED`/`REJECTED`), requested_at, reviewed_at/by, reason; FK на Company/User; не более одной PENDING на пару |

Membership и JoinRequest — обязательно отдельные таблицы. Членство выражает текущий доступ; заявки сохраняют историю решений. Отзыв доступа не превращает старую APPROVED заявку в REJECTED. Повторная заявка после отказа создаёт новую запись; повторное обращение при существующем PENDING не создаёт дубль. Активный участник не подаёт заявку повторно.

Одобрение: условное изменение только PENDING → APPROVED, создание либо реактивация единственного membership с LIETOTAJS и запись аудита в одной транзакции. Прежняя привилегированная роль не восстанавливается автоматически. Конкурентное второе решение получает согласованный конфликт 409, без дублей. Отказ: PENDING → REJECTED с автором/временем/причиной, без предоставления доступа. История не удаляется при отзыве членства.

### Регистрация и «Jūsu uzņēmumi»

1. Публичный список возвращает только id, slug, name компаний, принимающих заявки; никаких пользователей и складских показателей.
2. Форма регистрации требует выбрать существующую активную компанию.
3. Backend атомарно создаёт глобальный активный USER и PENDING заявку; клиент не задаёт role/status/is_active.
4. JWT разрешает работу со своим профилем и заявками, но не складом.
5. Переход на `/companies` — «Jūsu uzņēmumi». Доступных компаний сначала нет; PENDING отображается отдельно от доступных компаний.
6. VADITAJS видит очередь только своей компании; ADMIN — выбранной компании. На первом этапе это очередь UI, а не обещание email-доставки.
7. После одобрения активная компания появляется в списке доступных; после отказа показывается результат заявки. Обновление списка через refetch/кнопку обновления; push не обязателен.
8. Вход в компанию повторно проверяется backend. Для ADMIN отдельное отображение системного доступа не смешивается со списком одобренных членств.

Ожидание заявки нельзя реализовать через `User.is_active=False`: пользователь должен иметь возможность войти и видеть результат. Вход существующего аккаунта ведёт на `/companies`; новый запрос к другой компании создаётся без повторной регистрации.

## 4. Маршруты и серверный контекст

Планируемые frontend-маршруты: `/companies`, `/companies/[companyId]` (dashboard), `/companies/[companyId]/items`, `/categories`, `/locations`, `/suppliers`, `/transfers`, `/reports`, `/activity`, `/members`, `/requests` — последние сегменты всегда внутри `/companies/[companyId]`. Глобальная панель ADMIN должна оставаться отдельной от управления участниками компании.

Планируемое API: `/api/companies/{company_id}/...` для склада, участников и решений; отдельные identity endpoints `/api/auth/*`, собственные списки `/api/me/companies` и `/api/me/join-requests`, минимальный публичный список компаний. Точные схемы новых контрактов фиксируются до реализации соответствующих задач. Существующие unscoped API нельзя оставлять обходным путём.

URL — источник выбранной компании конкретной вкладки. Zustand может хранить последнюю выбранную компанию для удобства, но не авторитетное право доступа. Нельзя хранить единственную активную компанию глобально в User на сервере: вкладки должны независимо работать с разными компаниями.

Планируемая зависимость `get_company_context` в `backend/app/auth/dependencies.py` либо отдельном модуле:

1. Вызвать `get_current_user`; проверить JWT и глобальную активность.
2. Прочитать company_id из маршрута; проверить существование и активность компании.
3. Загрузить активный membership и его локальную роль либо проверить явное системное полномочие ADMIN.
4. Проверить требуемое разрешение; вернуть неизменяемый контекст user/company/membership/permissions и признак системного доступа.
5. Любая складская операция получает контекст обязательно; отсутствие контекста означает запрет, не выбор компании по умолчанию.

401 — нет действующей идентичности; 403 — нет права на выбранную компанию/операцию; 404 — предметный ID отсутствует в доступной компании. Для чужого и несуществующего связанного ID одинаковая нейтральная ошибка без раскрытия данных.

Сервис/репозиторий ищет по `(company_id, id)`, а не `db.get(Model,id)`. Контекст применяется ко всем спискам, detail, мутациям, фильтрам, totals, joins и агрегатам до сортировки/пагинации/limit. `company_id` устанавливается сервером, его смена обычным PUT/PATCH запрещена. ID категории, поставщика, места и перемещения проверяются в том же контексте. Передача чужого company_id в URL, query, headers или body не даёт доступа.

Отчёты и dashboard считают только выбранную компанию. Товары группируются по ID, а название — подпись, чтобы одноимённые товары не объединялись. `log_activity` получает контекст; событие сохраняет company_id в момент действия и не выводит владение из текущих членств автора. Системные события без компании отделены и доступны только ADMIN.

## 5. Владение и ограничения БД

Company-owned: `items`, `categories`, `locations`, `suppliers`, `transfers`, company-события `activity_logs`, новые memberships/requests и будущие остатки по местам. Для них company_id обязателен после завершения перехода. Глобальные: users, реестр companies и явно обозначенные системные события. Reports/dashboard — вычисления, отдельных таблиц сейчас нет.

- UNIQUE(company_id, sku/name/code) вместо нынешних глобальных ограничений соответственно для товаров, категорий, мест и перемещений.
- Supplier: UNIQUE(company_id,name) и UNIQUE(company_id,email), сохраняя текущую семантику внутри компании. User.email остаётся глобально уникальным с согласованной нормализацией.
- У родителей объявить UNIQUE(company_id,id); дочерние составные FK связывают `(company_id, foreign_id)` с соответствующим родителем. Применить к товару и всем трём предметным ссылкам Transfer.
- Nullable supplier_id допустим, но составной FK с обычным ON DELETE SET NULL может обнулить также company_id. Для первой версии использовать RESTRICT/архивацию поставщика; явное отсоединение поставщика меняет только supplier_id. Проверить соответствие текущему запрету удаления поставщика с товарами.
- Не каскадировать удаление пользователя/членства на складскую историю; хранить авторство. Creator глобален и может позднее потерять членство; право на создание проверяется во время операции.
- CHECK допустимых ролей/статусов, положительной quantity, неотрицательных остатков; индексы с company_id для списков и агрегатов.
- Единственный PENDING на пару обеспечить ограничением БД (например, частичным уникальным индексом SQLite), а не только предварительным SELECT.
- Tenant-события имеют company_id NOT NULL. Если системные события остаются в той же таблице, нужен явный scope и CHECK соответствия scope/company_id; NULL не должен становиться обходом tenant-фильтра.
- SQLite foreign_keys=ON обязателен для каждого соединения приложения, тестов и миграционных проверок. Составные FK защищают связи, но сами по себе не защищают SELECT от пропущенного фильтра.

## 6. Миграция и ручное владение прежними данными

**Владелец существующих записей неизвестен. Автоматически назначать TechStore, копировать всё на три компании или считать автора события владельцем запрещено.**

До backfill ответственный владелец проекта утверждает реестр: таблица/ID либо проверяемый набор ID → целевая компания → основание → согласовавший → дата. Отдельный реестр: user_id → компании → локальные роли, плюс первоначальные руководители. Для каждого Transfer товар и оба места должны получить одну компанию. Общие справочники, конфликтующие связи и неоднозначные/осиротевшие ActivityLog требуют ручного решения. Миграция останавливается на нерешённых строках.

Допустимы только явно утверждённые варианты: весь прежний набор принадлежит одной названной компании; либо согласованный раздел по связанным наборам; либо отдельная компания прежней системы. Создание такой четвёртой компании не считается утверждённым требованием и требует решения владельца. Демо-названия не служат доказательством владения.

Порядок expand → backfill → переключение → contract:

1. MT-02 устраняет небезопасную инициализацию тестов; MT-03 вводит Alembic и базовую ревизию, сверенную с реальной схемой. Не выполнять слепой stamp неизвестной БД.
2. На восстановленной копии проверить миграции; снять согласованную резервную копию перед рабочими изменениями. Добавить новые таблицы и временно nullable company_id без потери старых ID/паролей/связей.
3. До готовности изоляции не открывать новые компании. Если переходный старый API нужен, он работает только с явно сопоставленным прежним набором и проверенным доступом.
4. Backfill выполнять по утверждённому реестру, с остановкой записей либо согласованной стратегией, исключающей появление несопоставленных строк. Сверить количества, значения и граф связей.
5. Создать членства по отдельному реестру; глобальный USER не даёт всеобщего членства, глобальный ADMIN сохраняется. User.is_active и password_hash сохраняются.
6. Согласованно переключить backend/frontend; закрыть публичные и unscoped обходы. Старые JWT с sub/exp допустимы лишь через новые проверки; совместимость формата не равна доступу.
7. После проверки всех путей записи ввести NOT NULL, составные FK/UNIQUE и убрать переходные механизмы. create_all больше не заменяет миграции.

Не гарантируется безопасный downgrade после новых пользовательских записей. Откат — согласованное восстановление приложения и БД одной версии, с остановкой записей и учётом изменений после резервной копии. Старое приложение с общей выборкой нельзя запускать на БД с несколькими доступными компаниями.

## 7. Frontend-кеш и инвалидирование сессии

- Ключ каждого tenant-запроса содержит userId, companyId, ресурс и параметры; списки собственных компаний/заявок также разделены по userId.
- Query function и mutation фиксируют companyId в момент вызова; не читают изменяемую глобальную компанию после отправки.
- До проверки идентичности/контекста запросы отключены. Старые данные не используются как placeholder между компаниями.
- Logout, смена аккаунта и 401: отменить запросы, очистить кеш и чувствительные формы, сбросить token/user/контекст. Поздний ответ предыдущей сессии не восстанавливает данные; применить AbortSignal и проверку поколения сессии.
- Смена компании: отменить старые чтения, очистить/размонтировать формы, показывать только новый ключ кеша. Мутация, начатая в A, завершается и инвалидирует A, а не B; переключение при опасной незавершённой форме должно быть явно обработано.
- Отзыв членства/деактивация компании: удалить её кеш, закрыть формы, перейти на `/companies`; 403 не должен разлогинивать из других разрешённых компаний.
- После восстановления сессии запросить `/auth/me` и доступные компании. Сохранённая роль — не источник разрешений. Между вкладками синхронизировать logout/смену идентичности; выбранные компании вкладок остаются независимыми.
- Инвалидация после товара затрагивает items, categories, locations, dashboard, reports той же компании; после перемещения также transfers и activity. После решения заявки — заявки, memberships и доступные компании затронутого пользователя при следующем refetch.

## 8. Риски, открытые решения и демоданные

| Риск / решение | Требование перед выпуском |
|---|---|
| Неизвестное владение legacy | Ручной реестр из раздела 6; блокирует backfill и выпуск |
| Частичные перемещения | До MT-09 выбрать корректную модель остатков по местам либо явно согласованное временное ограничение только полным остатком. Второй вариант меняет возможности UI/API и не считается автоматически одобренным |
| История частичных done | Не пересчитывать реальные остатки автоматически по журналу; сверить фактические остатки и открытые резервы вручную |
| Конкурентные резервы и решения | Атомарные транзакции/условные обновления, ограничения БД, тесты гонок; повторное done не списывает дважды |
| Изменение Item.stock/location при активном Transfer | Проверяемая политика запрета либо согласованного пересчёта резервов; до её реализации нельзя считать учёт безопасным |
| Публичные `/items`, `/categories`, `/catalog` | До открытия компаний убрать доступ к внутренним данным. Сохранение публичного каталога возможно только отдельным утверждённым контрактом публикации и сокращённой схемой, не текущим ItemOut |

| Глобальный `user_update` | Не переиспользовать для VADITAJS; отдельное управление membership и защита повышения привилегий |
| Общие кеши и устаревшие роли | Требования раздела 7, тесты задержанных ответов и двух вкладок |
| Встроенный JWT secret и demo-пароли | До публичного выпуска обязательный секрет окружения, отсутствие demo-учётных данных; токен localStorage доступен JS, нужна защита от XSS. Переход на cookie — отдельное решение, не часть MT-01 |
| Ошибки агрегатов и журнала | Фильтр до aggregate/limit, безопасные DTO, отсутствие чужих имён/сумм/сообщений, аудит решений и системного доступа |
| Нет миграций; тестовый import пишет БД | MT-02/03 обязательны до экспериментов со схемой |

Право VADITAJS назначать других руководителей, необходимость email-уведомлений и сохранение публичного каталога остаются отдельными продуктовыми решениями. Для первой версии действует консервативная матрица раздела 2 и очередь заявок в UI. Это не блокирует подготовку схемы, но менять политику молча нельзя.

Три демонстрационные компании: SIA TechStore — электроника; SIA AutoParts — автозапчасти; SIA BuildMaster — строительные материалы. Это новые независимые наборы, не распределение legacy по догадке.

Новый demo-seed разрабатывается в MT-17 и запускается только явно. Стабильные slug и tenant-ключи, транзакции, создание только отсутствующих записей, конфликт вместо перезаписи. Не менять пароли, роли, цены и остатки существующих записей. Повторный запуск не создаёт дублей; ошибка откатывает соответствующую транзакцию. Предпочтительна отдельная demo-БД. В MT-01 seed не запускается.

## 10. Приёмка архитектуры и будущей реализации

MT-01 завершает только подготовку двух документов. Открытые решения не скрываются и не означают разрешение на миграцию.

- [ ] До backfill утверждено владение каждой прежней записью и членство старых пользователей.
- [ ] До MT-09 утверждена семантика частичных перемещений и сверка исторических остатков.
- [ ] Все tenant endpoints требуют контекст; ADMIN использует явный системный путь.
- [ ] Гость, PENDING, REJECTED и отозванный участник не читают склад напрямую.
- [ ] VADITAJS компании A не решает заявки и не управляет данными компании B.
- [ ] Один пользователь имеет разные роли в A/B без переноса привилегий.
- [ ] Составные FK отклоняют межфирменные связи даже при прямой записи в тестовую БД.
- [ ] Кеш, формы, отчёты и журнал не раскрывают предыдущую компанию/сессию.
- [ ] Legacy ID/пароли/история сохранены; demo-seed не перезаписывает записи.
- [ ] Выпуск нескольких компаний запрещён до завершения G4–G6 из чеклиста.

В MT-01 выполнено статическое чтение исходников; приложение, pytest, seed и миграции не запускались. Источники повторно проверены, а не приняты только из предыдущего аудита.
